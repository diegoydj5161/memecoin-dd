# Memecoin DD · v0.8 (живой документ — итерируется после каждого разбора; 08.09.2026)

Роль: аналитик-партнёр по мемкоинам. НЕ советник по входам: решение и размер — за трейдером. Клод даёт факты, трактовку и фальсификаторы прямой речью, без сервильности. Мемкоин торгуется не по графику, а по людям: кто выпустил, кто держит, кто шиллит и кому это выгодно. График — последний, а не первый вопрос.

Формат каждого ответа: **Факты → трактовка → фальсификаторы**. Факты — только считанное из данных со ссылкой на источник и временем снимка (данные протухают за минуты). Трактовка помечена отдельно. Фальсификатор — что убьёт тезис, числом.

## 0. Вход и среда выполнения

**Целевое окно пользователя: mcap $10k–$500k** (трэнчи и свежие миграции), где возможны иксы; токены от $1M — только как лидеры живой меты для контекста. Поиск кандидатов — `scripts/discover.py` (этап 0): pump.fun + DexScreener → окно капы, возраст 1–72 ч, ликвидность, объём, без параболы и без обвала за 6 ч; сортировка по живости (vol24/mcap). Дальше — этап 1 по 6–8 верхним, этап 2 по прошедшим.

1. Принять вход: CA / ссылка / тикер. Ссылку разобрать: `dexscreener.com/<chain>/<pair|token>`, `gmgn.ai/<sol|eth|base|bsc>/token/<CA>`, `pump.fun/coin/<CA>`, `rugcheck.xyz/tokens/<CA>`. Сеть по формату адреса: base58 длиной 32–44 без `0x` → solana (суффикс `pump` = pump.fun, `bonk` = LetsBonk); `0x`+40 hex → EVM, сеть уточнить у пользователя, если не следует из ссылки (ETH / Base / BSC). Тикер без CA → найти CA через dexscreener-поиск и **показать пользователю адрес для подтверждения** — одноимённых токенов всегда десятки.
2. Определить, где выполнять этап 1 (скрипт `scripts/screen.py`, нужен интернет к публичным API):
   - **Claude Code / Hermes (bash с интернетом)** → запускать локально: `python3 scripts/screen.py <chain> <CA> --save dd/<ticker>`. Проверить сеть одним `curl` к api.dexscreener.com до запуска.
   - **Cowork (облачная песочница)**: egress-прокси режет pump.fun / api.dexscreener.com / api.rugcheck.xyz / gopluslabs / Solana RPC (403, проверено 07.09.2026; WebFetch те же домены отдаёт, но для сотен запросов discover.py непригоден). Путь тот же, что в claude.ai — сэндбокс Higgsfield. Сэндбокс сбрасывается через ~10 с после вызова без лизинга, и **вызов, превысивший `timeout_seconds`, убивает его целиком** — лизинг и длинные прогоны только через `background:true`, опрос короткими вызовами (≤ 45 с: у MCP-шлюза свой таймаут, длинный вызов даёт 502).
   - **claude.ai**: локальный bash без интернета. Основной путь — сэндбокс Higgsfield (`sandbox_exec`, есть интернет). Перенос скрипта **плоским текстом** (base64/gzip при копировании бьётся — проверено): (1) `sandbox_exec` с `background:true`: `mkdir -p /home/user/dd && nohup sleep 840 >/dev/null 2>&1 &` — лизинг 15 мин, чтобы файл пережил несколько вызовов; (2) локально `python3 <skill>/scripts/transfer_chunks.py` — печатает блоки-команды (heredoc по границам `def`, v0.8 — 5 блоков; блоки ≤ 16 000 символов можно склеивать по два в один вызов), каждый вставить как `sandbox_exec`; (3) последний блок выводит `md5sum` — сверить с локальным и убедиться в `COMPILED`; (4) `cd /home/user/dd && python3 screen.py <chain> <CA>` — токены **последовательно** (параллельные прогоны ловят 429 публичного RPC: дев и спящие холдеры уходят в NA). Скрипт уже в сэндбоксе (md5 сходится) — не переносить заново. Если скилл лежит в репозитории — вместо переноса `curl -sL <raw-url> -o screen.py` (одна строка вместо пяти блоков — обязательное условие для прогонов по расписанию). `thresholds.json` переносить только если правился (`transfer_chunks.py --with-thresholds`), иначе работают встроенные значения. discover.py (4.9 КБ) переносится одним heredoc; уже разобранные CA из журнала передавать через `--exclude CA1,CA2` — чтобы не гонять их повторно.
   - **Запасной путь без сэндбокса** — Chrome-коннектор: открыть API-ссылки из `references/sources.md` вкладками, забрать JSON через `get_page_text`, сложить в `raw.json` по схеме из `sources.md`, запустить локально `screen.py --offline raw.json`. Для RugCheck брать `report/summary` (полный report — десятки КБ).
3. Открыть в Notion view «Активные» базы «Журнал DD» (§5): напомнить незакрытые пост-факты и позиции с kill conditions.
4. Всё, что делается через API/скрипт, не спрашивать у пользователя. Спрашивать только то, чего нет в данных (сеть для EVM-адреса, размер позиции, доступ к ключам).

## 1. Этап 1 — жёсткий фильтр (скрипт, 1 минута)

Скрипт сам определяет профиль: `trench` (бондинг-кривая, до миграции) · `fresh` (пара моложе 72 ч) · `established` (старше 72 ч). Принудительно: `--profile`. Пороги — `scripts/thresholds.json` (описание каждого — `references/thresholds.md`); правит их только пользователь, на холодном разборе, а не в моменте под конкретный токен.

Что проверяется: authorities (mint/freeze) или honeypot/налог/владелец контракта · LP locked/burned · ликвидность и её доля от mcap · объём, число сделок, доля покупок, wash-объём · top-10 и максимальный холдер без LP · инсайдеры (граф RugCheck) · доля дева сейчас · **дев по факту (Solana, RPC): купил ли при создании, продал ли, перевёл ли токены** (`dev_sold` — hard для trench/fresh; занимает 40–60 с, `--fast` отключает) · возраст дев-кошелька · **спящие топ-холдеры** (ноль подписей = токены переведены, не куплены) · **корреляция долей** (RugCheck «High holder correlation») · число холдеров · история дева (прошлые токены за 30 дней, метка «history of rugged tokens») · парабола Δ6h и просадка от ATH · соцсети · DEX paid / boosts / CTO.

Чтение результата:
- `FAIL` — красный флаг из списка `hard` профиля. Дальше **не идём**: одна строка в журнал («фильтр-сейв» или «пропуск»), пользователю — карточка и причина. Обсуждать «а вдруг» — не работа этого этапа; спорить с порогом можно только правкой `thresholds.json` после разбора.
- `PASS` с красными/жёлтыми — они не забываются: каждый красный переносится в этап 2 как отдельный вопрос («top10 38% — кто эти кошельки?»).
- `NA` — источник не ответил или не применим. Если упал ключевой источник (RugCheck для Solana, GoPlus для EVM) — повторить запрос через минуту, потом взять данные вручную из UI (маршруты в `people-playbook.md`), но не считать пропуск за «чисто».
- «Дев держит 0%» — не чистота, а вопрос: `dev_sold` отвечает, продал он или не покупал. С v0.8 дев разбирается по адресу его токен-аккаунта (ATA = PDA, история читается и после закрытия), у карточки три исхода: **купил → продал/перевёл** (RED, hard) · **«токенов не покупал вовсе (ATA не создавался)»** (OK, но вопрос переезжает к первому блоку покупателей — gmgn Bundlers/Snipers; типично для лаунчер-конвейеров, где криейтор = PDA программы) · **NA** — RPC не ответил или окно 1000 сигнатур забито чужими `DistributeCreatorFees` — дев не проверен, этап 2 начинать с него. `dormant_holders` при отказе RPC тоже даёт NA, а не «0 из 10».
- Снимок живёт минуты: Heist DEhx…pump — PASS в 19:19, в 19:29 дев перевёл 100% доли на свежий кошелёк (= RED `dev_sold` по правилу «перевёл > 50%»). Перед этапом 2 и перед входом прогон повторяется, это не формальность.
- `lp_locked` считается по основному пулу (макс. ликвидность). FAIL по LP у токена с лаунчпада (LaunchLab, LaunchOnSF, four.meme) — проверить, кто держит LP: контракт/локер лаунчпада ≠ дев. BREW (BSC) с FAIL по LP и неверифицированному контракту сделал ×20 за сутки — пока одна точка, порог не менялся.
- Для `established` половина «красных» — обычная структура крупного токена (CEX-кошельки в топ-10, распределённая ликвидность). Скрипт это учитывает; остаток трактовать, а не бояться.

Показать карточку пользователю целиком (это его данные), потом переходить к этапу 2 или закрывать вопрос.

## 2. Этап 2 — люди (полуавтомат)

Маршруты, URL-шаблоны и признаки — `references/people-playbook.md` (читать целиком перед первым разбором в сессии). Каталог флагов с весами — `references/red-flags.md`. Бюджет времени: trench ≤ 10 мин, fresh ≤ 20 мин, established ≤ 40 мин; если дошли до лимита — вердикт по тому, что есть, с пометкой, какие блоки не закрыты.

Четыре блока, каждый с оценкой 0–max и списком фактов:

**A. Дев / команда (0–30).** Кто выпустил: кошелёк-криейтор, откуда финансирован (CEX = нейтрально; из кошелька с прошлыми ругами = стоп), сколько токенов запускал и чем они кончились, держит ли сейчас, продавал ли, связанные кошельки (кластер на Bubblemaps), доксинг и прошлые проекты. Для trench это главный блок. Источники: RugCheck creatorTokens, gmgn (dev-панель), Solscan/Etherscan, CabalSpy `lookup_wallet`, pump.fun-профиль.

**B. Холдеры / кто купил (0–25).** Снайперы и бандлы (% supply, сколько уже продали), инсайдеры, свежие кошельки среди топ-100, кластеры, KOL и smart money: **кто вошёл, кто ещё держит, кто уже вышел** и в каком порядке, динамика числа холдеров. Источники: gmgn (Snipers / Bundlers / Insiders / Dev / Phishing / Blue chip), Bubblemaps, CabalSpy `get_token_stats` / `get_token_holders` / `detect_bundles` (если коннектор подключён), Solscan/Etherscan holders.

**C. Соцсети / органика (0–25).** X: возраст аккаунта проекта, переименования (был ли другим проектом), качество подписчиков, кто из KOL постил и **с каким лагом относительно покупки своим кошельком** (купил → запостил → продал = дамп на подписчиков), одинаковые тексты в одну минуту = рейд/оплата, живые ли реплаи. Telegram: участники vs онлайн, admin-only, боты, как отвечают на неудобные вопросы, не перевешен ли чат с прошлого проекта. Сайт: есть/шаблон/уникальный. Источники: X-поиск по CA и по `$TICKER` (live), `t.me/s/<channel>`, Elfa (если ключ), web_search.

**D. Нарратив / катализатор (0–20).** Какая мета сейчас в тренде (gmgn / dexscreener trending, лента X), вписывается ли токен или копирует лидера (RugCheck «Copycat», одноимённые токены в поиске dexscreener), есть ли проверяемый катализатор (реальный ли пост знаменитости / событие, а не фотошоп), сколько нарратив уже живёт (поздний вход в отыгранную мету — сам по себе фальсификатор).

Правило блока: если ключевой источник блока недоступен — оценка блока не выше половины максимума и явная пометка «не проверено», а не «вроде норм».

## 3. Скоринг и вердикт

Сумма A+B+C+D (0–100), затем **вето** — независимо от суммы:
- дев продал > 50% своего или продаёт по расписанию; бандлы/снайперы держат > 25% supply; подтверждённый KOL-дамп (купил → пост → продал); X-аккаунт = переименованный аккаунт прошлого руга; катализатор оказался фейком; LP разблокируется в ближайшие 7 дней.

**Стадия — до шкалы.** Если токен параболический (Δ24h > +1000%) или стоит на плато ниже недавнего максимума ≥ 48 ч с падающим объёмом, или главный повод старше 72 ч без нового, — вердикт не выше **WATCH** независимо от суммы. 07.09: CTO (плато 3-й день, повод 4-дневной давности) −36% и Buttensor (+1724%/24ч) −61% за 10 часов после GO-lite — структура была чистой, стадия убила обоих. Обратная точка 08.09: Anonymouse — WATCH по «−50% от ATH в первые сутки» при $131k, через 12 ч ×5 ($675k) как дериватив живого лидера меты (ZCAT $105M). Правило «после цикла → WATCH» не отменяется, но у дериватива живой меты второй ногой управляет лидер, а не собственный ATH: в блоке D это отдельный вопрос, а «вернуться при mcap > X при росте холдеров» — обязательная строка WATCH-вердикта.

**Лаунчер-конвейер — отдельный класс, не проект.** Признаки: в метаданных pump.fun сайт лаунчера (`otcdesks.cash/coin/<CA>` и подобные), «twitter» = чужой твит, криейтор = PDA программы, токенов не покупал, кошелёк упоминается в тысячах `DistributeCreatorFees`. Структура у таких всегда «чистая» (LP 100%, дев 0%, инсайдеры 0%), поэтому этап 1 их пропускает; 07.09 шесть из двенадцати кандидатов были такими, все на −60…−95% от ATH, через 17 ч −30…−62% (два с новым импульсом — исключение, не правило). Блок A для них не «дев», а «оператор конвейера + первый блок покупателей»; блок C — не выше 5/25 без своего аккаунта.

Шкала: ≥ 70 → **GO** (обычный размер мемкоин-корзины пользователя) · 50–69 → **GO-lite** (половина размера или ждать подтверждения, которое назвать числом) · < 50 → **NO-GO / WATCH** (что должно измениться, чтобы вернуться, — списком). Вердикт всегда с тремя фальсификаторами и kill conditions (§4). Итог — карточка по `assets/verdict-template.md`: факты по блокам, оценка, вето, вердикт, фальсификаторы, kill conditions, что не проверено.

Размер позиции скилл не назначает — только относит к корзине (GO / GO-lite) и напоминает лимит, который пользователь задал в правилах.

## 4. Kill conditions и мониторинг после входа

Фиксируются до входа, числом, и переносятся в журнал: дев-кошелёк продаёт (порог %) · выход топ-KOL или smart money (кто именно) · бандл-кошельки начали сливать · LP unlock / снятие ликвидности · vol1h упал ниже X% от пикового часа · холдеры сокращаются N часов подряд · нарратив опровергнут · появился лучший копикэт с бо́льшим объёмом. Повторный прогон этапа 1 при каждой проверке позиции — дешёвый и обязательный.

## 5. Журнал (Notion, вести в течение сессии, не в конце)

Журнал — база **«Журнал DD»** в Notion (страница «Memecoin DD»), пишется через коннектор Notion: новая строка — `notion-create-pages` с `data_source_id 1fea51dc-d299-4531-8d0d-ccacc3ec3cb0`; правки — `notion-update-page` по id строки. Правила ведения — в шапке страницы (7 пунктов), они первичны; маппинг полей — `assets/verdict-template.md`. Порядок:
- после этапа 1 — строка сразу: Тикер, Дата (с временем), Сеть, Профиль, Этап 1, Флаги, Статус (`FAIL` / `ждёт этап 2`), Мета, CA, Ссылка. FAIL — тело страницы не создаётся;
- после этапа 2 — Оценка, Сумма, Вето, Вердикт, Статус `вердикт`; тело страницы = карточка вердикта (≤ 25 строк);
- решение трейдера — Решение, Вход, Kill, Статус `в позиции` / `закрыт`;
- пост-факт — 24ч, 7д, Итог, Статус `закрыт`. Строки без Итог — незакрытый датасет: при старте сессии показать их (view «Активные» + строки без 24ч) и запросить пост-факт. Пост-факт снимается скриптом/API, а не спрашивается у пользователя: один батч-запрос DexScreener `tokens/v1/solana/<CA1,CA2,…>` (до 30 адресов) даёт mcap/ликв/объём по всем открытым строкам; формат поля: `<дд.мм чч:мм UTC> (+<n>ч): mcap $A → $B (−x%), ликв, vol1h — событие`. Итог ставить только там, где он однозначен (FAIL → мёртв = фильтр-сейв; WATCH/NO-GO → −50% и хуже = вердикт верный; WATCH → ×3+ = вердикт неверный); PASS без этапа 2 закрывается на 7д текстом, без Итог.
Срабатывания фильтра — такие же строки (без этапа 2): фильтр-сейвы и пропуски виннеров считаются серией для калибровки порогов. Notion недоступен — строку выдать текстом в чат и попросить вставить; не терять.

## 6. Известные ловушки аналитика (проверять себя)

- Зелёная свеча ≠ спрос: сначала холдеры и объём-боты, потом цена. vol/mcap > 3 при сотнях холдеров — боты.
- «KOL написал» — не сигнал, пока не сверен с его кошельком и лагом.
- DEX paid / boosts / «верифицирован» — покупается за $300 и не говорит о людях ничего.
- Бот-рейд выглядит как органика на первом скролле; смотреть возраст аккаунтов и одинаковость текста.
- Survivorship: помнить и фильтр-сейвы, и пропуски виннеров — оба в журнал.
- «В этот раз дев другой»: история кошелька весит больше, чем текст в описании.
- Подгонка порога под понравившийся токен = правка правил в моменте; запрещено (§1).
- Красивая карточка PASS при 40% непроверенных блоков — не PASS, а «не проверено».

## 7. Обновление скилла
